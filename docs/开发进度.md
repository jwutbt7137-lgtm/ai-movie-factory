## 五、关键设计

### 1. 分段与分层摘要

1. 只用已识别的对白作为证据；没有对白或对白过少直接拒绝分析。
2. 按 `chunk_target_chars`、`chunk_max_duration_s` 和 90 秒长静默切分；过短尾段合并。
3. 每段发送：时间范围、镜头编号/时间、对白编号/时间/文本；不发送视频、关键帧、本机路径。
4. 每段要求返回 JSON：summary/events/characters/conflicts/turning_points/uncertainties/confidence。
5. 本地校验证据编号；无证据事实移除，部分无效引用过滤；记录警告。
6. 整片整合只使用分段结构化结果，生成标题、梗概、主题、人物关系、转折、未决问题。
7. 整片分析始终标记 `needs_review=True`，并说明“未使用视觉信息”。

### 2. 文案生成与版本

1. 使用整片分析作为唯一事实来源，要求每段给出 `segment_ids`/对白证据。
2. 本地把 `segment_ids` 映射到镜头与事件描述，写入 `shot_ids/event_descriptions`。
3. 无效片段引用会被移除并标记待核实；字数偏差、分析段不足、token 截断写入警告。
4. 版本由数据库递增分配；生成/人工编辑都创建新版本；恢复版本只切换 `is_current`。
5. 人工编辑按空行/单行拆段；可继承原段落的剧情/镜头关联；新段落标记无关联。

### 3. 费用与预算

- 单价来自配置（元/百万 tokens），费用根据接口 `usage` 计算；usage 缺失时按保守规则估算并标记 `tokens_estimated`。
- 调用前用 prompt 字符 + `max_tokens` 做保守预检；预计超预算则停止并要求确认。
- 客户端在每个付费调用前再次检查项目已用费用；除非用户确认超支，否则不发请求。
- 相同请求命中 SQLite 缓存时费用为 0；缓存键包含 Base URL、模型、purpose、messages、temperature、max_tokens。
- 失败调用也记录一条账目（费用 0、错误摘要），便于排查。
- 预算上限 0 表示不限制；实际账单仍以 DeepSeek 为准。

### 4. 配音与时间轴

1. 按句末标点切句，过长按逗号/冒号再切；每句继承段落镜头/证据元数据。
2. 逐句合成并缓存；Edge 输出 MP3，Piper 输出 WAV；每句用真实音频时长定位。
3. 句间/段间停顿进入时间轴；完整音轨按同一停顿重新混音为 48kHz WAV。
4. 主引擎逐句失败时尝试备用引擎；全失败报错，不生成静音假音频。
5. 音频缓存键包含引擎/声音/语速/音量/音高/文本。

### 5. 镜头匹配

1. 候选镜头 = 文案段落镜头 ∪ 剧情片段镜头，按序号排序。
2. 从上一句结束镜头之后推进，避免每句回跳片头；累加时长到“配音时长 + 余量”。
3. 不足时用紧邻的后续镜头补足；标记时长不足/复用。
4. 置信度由来源、覆盖、连续性组成；无视觉语义时上限 0.70，并全部标记人工审核。
5. 不把启发式结果包装成“语义匹配”；第四阶段提供逐句手动换镜。

### 6. 视频合成

1. 视频槽位 = 下一句开始 - 本句开始，包含句后停顿；最后一句到配音总时长。
2. 逐句裁切镜头，统一分辨率/fps/SAR，按镜头序号拼接；不足补冻结帧，超出裁掉。
3. 每句先生成短滤镜的临时 H.264 片段，再用 concat demuxer 拼接，避 Windows 命令行长度限制。
4. 最终一步烧录 ASS、混入完整配音/可选 BGM、AAC 编码、faststart 输出。
5. SRT/ASS 边车始终保存；取消删除半成品；结果写入 `exports`。

### 7. 安全与隐私

- API Key 只读环境变量；不写入配置、数据库、日志。
- 请求/响应正文不写日志；错误体截断并脱敏。
- 影片音视频/关键帧不发送给 DeepSeek；只发送对白文本、时间与镜头编号。
- 不进行 DRM 破解、加密解密、版权规避。
- 第二阶段自动化测试没有真实 DeepSeek 调用；真实联调是用户明确授权后单独执行，见 `真实微电影测试.md`。
- Edge TTS 只发送解说文案文本；影片、关键帧、对白原文件不发送。Piper 可完全离线。

## 六、数据结构与数据库

新增 SQLite 表：

- `story_analysis`：项目 ID 主键、完整分析 JSON、模型、创建时间、时间轴生成时间。
- `scripts`：文案版本；项目、递增版本、风格、标题、字数、payload、来源（AI/人工编辑）、模型、费用、是否当前。
- `api_calls`：每次调用/缓存命中/失败；用途、模型、输入/输出/总 token、费用、缓存标记、状态、耗时、错误、请求哈希、是否估算 token。
- `llm_cache`：请求哈希 → 响应内容、模型、token、创建时间。
- `voiceovers`：一次配音的完整 JSON（逐句时间轴）、音频路径、总时长、是否当前。
- `shot_matches`：一次镜头匹配的完整 JSON、关联文案/配音、是否当前。
- `exports`：一次成片结果 JSON、输出路径、关联方案/配音、是否当前。

新增 Pydantic 模型：`StoryAnalysis`、`StorySegment`、`PlotEvent`、`Conflict`、`TurningPoint`、`StoryCharacter`、`CharacterRelation`、`Script`、`ScriptParagraph`、`ScriptSummary`、`SpeechUnit`、`Voiceover`、`ShotSelection`、`ShotMatchPlan`、`ExportResult`、`ApiCallRecord`、`CostSummary`。

## 八、已知问题与限制

1. **仅验证了英文 CC 短片**：中文真实影片、长片、不同模型/账号网关尚未实测；费用为本地单价估算，实际账单以 DeepSeek 为准。
2. **文本分析只覆盖有对白片段**：Tears of Steel 对白在 07:02 结束，后 5 分钟画面/动作未进入分析。
3. 未接入视觉模型；关键帧不参与剧情分析，动作/场景/视觉线索需人工核对。
4. 剧情分析仍可能误读对白或把推断写成事实；本地证据校验只能约束“引用编号”，不能保证语义正确。
5. 文案原创性无法自动验证；只能靠提示词和人工审核。
6. 文案与剧情事件通过“段落 → 片段 → 事件”间接关联，未做逐事件引用计数。
7. 暂停在检查点生效；单次 HTTP 请求会先完成。
8. 长片/大量调用未做性能与成本压测；建议先用短片和低预算实测。
9. **镜头匹配无视觉语义**：只按片段/时长/连续性；全部需人工审核；手动换镜只能按序号勾选，不能裁切/拖拽/转场。
